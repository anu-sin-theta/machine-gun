### Real bugs found along the way (so nobody re-introduces them)

1. **TS `canonicalJson` was not RFC 8785.** It built an object in sorted order then `JSON.stringify`-ed it, but JavaScript enumerates integer-like keys (`"0"`, `"10"`) first regardless of insertion order, so `{"0":0,"":""}` came out as `{"0":0,"":""}` instead of `{"":"","0":0}`. Found by the Rust/TS differential test, fixed by hand-building the string, regression tests added. It was deterministic, so approval binding was never unsafe, but the hashes would not have matched any other implementation (or an HCS verifier).
2. **Link-intel missed lookalikes in subdomains** (`paypa1.com.account-verify.top`). I only ran the lookalike/swap/confusable checks on the registrable label. Now run over all host tokens. Found by probing the engine's actual signals after a score assertion failed.
3. **`LinkIntelConfig` serialised as `suspicious_tlds`** while everything else is camelCase. Fixed with `rename_all = "camelCase"`.
4. **JSON can't carry `NaN`/`Infinity`**: `JSON.stringify(NaN)` is `null`, so a non-finite `authTime` made Rust reject the input while TS returned `STALE_AUTH`. Rust now reads `null` as NaN (fails closed as `STALE_AUTH`).
5. **Next 16 `cacheComponents` is on** (from the scaffold): route handlers may not export `runtime`/`dynamic`, and a handler with no request-time API is **prerendered at build time**. The health check calls `await connection()` to stay dynamic. Remember this for every new route handler.

## Piece 5 notes

- HCS messages are canonical JSON (RFC 8785, via the Rust bridge), at most 1024 bytes, and hold **hashes and ids only**. `Published.hash` is the sha256 of the canonical message, so anyone can recompute it from the topic. Audit events: check received/verdict/decision, approval requested/approved/rejected, payment settled/blocked/failed, with `verdictHash`, `actionHash`, `zgRequestIds`, `txId`.
- **Reputation is weak evidence by design:** the topic is open to anyone who can pay for a message. Reports are validated, other payees ignored, one report per `checkId` (most severe wins). 1 flag gives medium; 2 flags or any dispute gives high; clean or empty history is low. It feeds `applyEvidenceFloor`, so it can only raise risk.

- `@hiero-ledger/sdk` is in `serverExternalPackages` (next.config.ts); `pnpm build` passes. No route imports the SDK yet, so bundling is not exercised.
- Private keys: `PrivateKey.fromStringDer` expects the DER hex from portal.hedera.com. A raw hex key would need `fromStringED25519` / `fromStringECDSA`.

## Piece 7 notes

- **Open question 1 (partly answered) from `https://auth.world.org/.well-known/openid-configuration` (Nov 7):** `acr_values_supported` is only `https://world.org/oidc/acr/orb` and `.../orb-face`. **There is no selfie tier advertised**, so the human tier now defaults to `[orb, orb-face]` and strong to `[orb-face]`, set through `WORLD_ACR_HUMAN` / `WORLD_ACR_STRONG` (validated: known URIs only, strong must be a subset of human). The cores' own defaults (which still list selfie) are untouched; the app always passes the configured set. Whether orb-face needs a particular credential on the test environment is still unknown.
- **Open question 2 (not answered):** we send `claims={"id_token":{"acr":{"essential":true,"values":[...]}}}` (the OIDC spec form). The issuer says `claims_parameter_supported: true`, but nobody has checked `values` vs `value` with a real login. Test it first when credentials exist.
- Other facts from discovery: auth code flow with S256 PKCE, `client_secret_post`/`basic`/`private_key_jwt`/`none` at the token endpoint, RS256, pairwise `sub`, `auth_time` and `amr` are issued, `prompt` supports `login`, and `authorization_response_iss_parameter_supported` is true (openid-client enforces the `iss` response parameter). Docs.world.org was not reachable; Agent Pass specifics (device flow, `amr`) come only from third-party hackathon notes and are not relied on.
- Flow: `startApproval` creates the pending approval via the Rust core and returns the World URL (`max_age=0`, `prompt=login`, PKCE, acr claims). `completeApproval` looks up the attempt by `state`, runs the OIDC exchange (signature, iss, aud, exp, state, nonce, PKCE by openid-client), then the Rust `validateApproval` (nonce, freshness, acr, action hash) and a single-use nonce check, then a compare-and-set `pending -> status`. Anything that goes wrong after the redirect leaves the attempt `rejected`; replays return `not_pending` and change nothing. `consumeApprovalOnce` is the only way to spend an approval (approved, unexpired, one winner).

## Piece 8 notes

- **Flow (`runCheck`):** create the check, probe the merchant's own 402 (payee and amount come only from there), private extraction (0G), buy reputation and link evidence over x402, judge (0G) with the evidence floor, `decide` (Rust), then block, start a World step-up, or auto-pay. Audit events and a payee reputation report go to HCS best-effort.
- **Money moves in one function, `payAndRecord`,** reached only from an `auto-pay` decision or `settleApproved` (which consumes the approval exactly once and refuses an approval that belongs to another check). Auto-pay reserves the daily budget *before* paying and blocks if the reservation overshoots, so concurrent auto-pays cannot exceed it (the over-reservation is kept, which is conservative).
- **Fail closed:** probe failure ends the check as `failed` before anything is read or paid. A failed 0G call is a missing verdict (strong step-up, never auto-pay). An unreachable checker is *medium* evidence. If the request text names a payee other than the merchant's `payTo`, that is *high* evidence.
- **SSRF guard:** the resource URL comes from the user, so the probe only fetches origins in `config.merchantOrigins` (the app's own origin plus `MERCHANT_ORIGINS`), never follows redirects, and requires a 402 with an HBAR `exact` option on the configured network.
- **Payment guards:** checkers get a per-call `SpendGuard` (payee = `HEDERA_PAYEE_ACCOUNT_ID`, cap 0.1 HBAR). The merchant gets a guard built from the probed challenge: that exact payee and at most that amount, so a price rise or payee change after the probe aborts before signing.
- **`/api/checks` spends money and 0G credits.** Set `API_TOKEN` (16+ chars) anywhere it is reachable; unset means open. `GET /api/checks/[id]` hides the input text. There are no per-user rate limits yet.
- Tests: 43 for the agent (24 pipeline scenarios with fakes incl. concurrency and replay, 19 for the real x402 ports against a fake x402 server). On a production build the routes returned the expected 401/400/503/404.
- **Not done / not verified:** the loop has never run with real 0G, Hedera, x402 settlement or World. `getAgentDeps` throws unless the Hedera agent keys and payee are set, and 0G/World keys are needed for their parts. Account linking (`subjectBinding`) is still unbuilt. The 'second opinion' checker is unbuilt. Reports on the reputation topic are only written for `paid-ok` and for high-risk hard blocks, not for denied/rejected approvals. A crash between consuming an approval and paying leaves the check `awaiting-approval` with a spent approval (no money moved; needs a manual retry path). Verdict/decision explanations are not stored in human-readable form for the UI yet.

## World ID simulation (added between pieces 8 and 9)

No World credentials exist yet, so `WORLD_MODE=simulated` runs the **same** flow against an issuer inside this app. Our code does not special-case it: `createWorldOidc` (openid-client) does discovery, PKCE, code exchange and ID-token validation exactly as it does against `auth.world.org`, and the Rust core does the same nonce, freshness, `acr` and action-hash checks. Only the issuer URL, client id and secret differ.

- **Consent page** (`/api/sim-world/authorize`): says it is a simulation, shows which `acr` was requested, and offers *orb-face*, *orb*, *selfie* and *deny*, marking which meet the request. That lets a demo show an approval, a too-weak login being rejected (`INSUFFICIENT_ASSURANCE`) and a denial.
- **Safety rails:** opt-in only (`WORLD_MODE=simulated`, default is real); the route 404s otherwise; real `WORLD_CLIENT_ID/SECRET` together with simulated mode is a config error so the two cannot be mixed up; the consent page only redirects to the one registered redirect URI; every approval is audited as `source:simulated` (`approval.approved` detail) so it is never passed off as a real World approval. **It checks nobody's identity: anyone who can reach the app can approve a payment. Never use it where real money can move.**
- **Statelessness:** authorization codes are HS256 JWTs, so any instance can redeem them, but the RSA signing key is per process unless `WORLD_SIM_KEY` (base64 PKCS#8 PEM) is set. On multi-instance hosting (Vercel) set `WORLD_SIM_KEY`, or the token endpoint and JWKS may be served by instances with different keys. `WORLD_SIM_SECRET` (16+ chars) replaces the built-in dev secret.
- Calls from our server to the simulator are in-process (`getApprovalDeps` wraps fetch), and `allowInsecure` lets openid-client talk to an `http://localhost` issuer. It is set only for the simulator and never for World.
- Tests: 38 simulator tests through the real openid-client path (all outcomes, request validation, token-endpoint attacks, expiry, key handling, config), 3 wiring tests booting `getApprovalDeps` in simulated mode, route gating, and the audit label. A production-server smoke test over HTTP served discovery, JWKS and the consent page, issued a code on approval, and returned 400 for a forged redirect URI.

## Marketplace: registry and dynamic verifier directory (added after piece 10)

The project was a one-agent payment firewall; this is the first step toward an agent marketplace. Full description, the verifier contract and the safety table: [docs/MARKETPLACE.md](docs/MARKETPLACE.md).

- **Code:** `src/marketplace/` (`types.ts` listing schema, `endpoint.ts` SSRF rules, `evidence.ts` relabel + clean, `select.ts`, `heuristics.ts`, `builtins.ts`, `directory.ts`, `public.ts`); `AgentsRepo` in `src/adapters/db` (memory + Postgres, table `agents`, migration `drizzle/0001_*.sql`); `GET /api/agents`; `/api/x402/checkers/domain-heuristics`; the "Verifier network" card on the page.
- **Pipeline change:** the fixed `checkers` port is gone. `deps.verifiers` has `list(kind)` (the directory's pick) and `call(listing, subject)`. `gather` consults every listed verifier per question. A failing verifier is medium evidence under its own name; an empty or unreadable directory is medium evidence named `verifier-directory`. `check.verdict` audit events carry `verifiers` (evidence names of those that answered).
- **Payment:** `callVerifier` (`src/agent/x402.ts`) re-validates the endpoint, checks the listing is an active verifier for that question and under the 0.1 HBAR ceiling, then pays through a guard for that listing's account and price, and returns evidence under the listing's name with the detail cleaned.
- **Demo mode** runs the same listings with local stand-ins (real analysis, no payment).
- **Bug caught by a test during this work:** adding `verifiers` to the audit event made the largest valid event ~1,090 bytes, over Hedera's 1,024-byte message limit (a valid event that could not be submitted). Fixed by recording the short evidence name instead of the id and tightening the other bounds (checkId 48, request ids 64, detail 100); a test pins the worst case under the limit. Oversized 0G request ids are truncated before auditing, because audit failures are swallowed by design.
- **Onboarding (added after the registry):** `src/marketplace/onboard.ts` (`registerAgent`, `proveControl`, `activateAgent`, `suspendAgent`), `POST /api/agents` (public, creates `suspended` after the endpoint's unpaid 402 names the listed payee/network/asset at no more than the listed price; 25 pending max), `POST /api/agents/[id]/status` (operator, needs `API_TOKEN`; activation re-proves control). ## Decisions log

- **Tracks:** Hedera x402, World Agent Pass, 0G Private Computer. Dropped "Agents That Pay for Themselves": HBAR earnings can't fund 0G compute without a bridge.
- **Stack:** one layered Next.js app in `machine-gun/`, Vercel + Neon, pure core with adapters behind interfaces.
- **Safety-critical core in Rust (WASM),** at the user's request: policy, approval binding, canonical JSON + hashing, assurance tiers, and the new link-intel engine. WASM (not napi, not a separate service) so it deploys to Vercel with no native binaries. Binary is inlined and committed because Vercel's build has no Rust toolchain.
- **TypeScript core kept as the spec.** Differential/property tests run both implementations on the same random inputs and require identical outputs, including identical failures.
- **JSON string boundary.** Money crosses as decimal strings, never numbers. Every WASM export returns an envelope `{"ok":true,"value":…}` / `{"ok":false,"error":{"kind","message"}}` and never throws or panics (`panic = "deny"` lints, `panic = "abort"` in release).
- **Fail closed everywhere:** missing/unknown verdict → high risk; non-finite `auth_time` → stale; any hashing failure → `ACTION_CHANGED`.
- **Approval binding is stored server-side** (World has no `authorization_details`); the action hash is re-checked on callback.
